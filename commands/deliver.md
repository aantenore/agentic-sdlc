Use the `agentic-sdlc` skill for this request.

Starter intent: **Turn this new requirement into an agreed work brief, implement it, verify it, and open a new pull request.**

Requirement: $ARGUMENTS

Rules for this command:

- The plugin root is `${CLAUDE_PLUGIN_ROOT}`. The deterministic CLI is `${CLAUDE_PLUGIN_ROOT}/bin/agentic-sdlc.mjs`; run it with `node` and pass `--root` for the target project.
- Follow the skill's `Required Delivery Order`. Do not skip a stage because it looks obvious.
- The delivery kind is `pull_request`. A prior pull-request choice is never reused: propose a delivery execution profile for this delivery and get it approved.
- When you propose the delivery, ask the code review question at the same step as the autonomy choice and before `task start`, with the exact Italian or English copy in the skill (Workflow step 13): does the user want a person who did not author the commits to approve the code before this PR is merged? Suggest “No”, and “Yes” when the story touches security, authentication, payments, data migrations, public APIs, or infrastructure. Pass the answer to `autonomy delivery propose` with `--code-review required|not-required --code-review-actor-type human --code-review-approval-source explicit-user --code-review-summary "<the user's words>"`. Never infer it, reuse an earlier answer, or answer for the user, and do not start the task without it. The review is checked only at merge.
- At the same step ask the merge question with the exact copy in the skill (Workflow step 13): how should merging this PR work? Options: `manual` (the user merges on GitHub, then runs `autonomy delivery reconcile`), `after-confirmation` (the plugin merges after a checkpoint the user confirms), or `automatic` (the plugin merges once every gate passes; needs `--merge-allowed` and is not allowed at level `supervised`). Pass the answer with `--merge manual|after-confirmation|automatic --merge-actor-type human --merge-approval-source explicit-user --merge-summary "<the user's words>"`. Never infer it, reuse an earlier answer, or answer for the user, and do not start the task without it.
- Each story gets its own pull request and autonomy choice. When the user wants one pull request for several parts, propose one delivery story with tasks at breakdown time, before any breakdown is approved.
- Include `.gitignore` in the requirement write paths whenever the work may add or change it.
- `pull_request.create` and `git.push` are authorized actions. They need an approved profile that names them; ask before the first remote-visible action.
- Put the recorded checks in the pull-request description: print them with `autonomy delivery checks --id <profile-id>` after the test, scan, and review evidence is recorded, and include the table unchanged. The `pull_request.create` authorization returns the same table as `pull_request_body_checks.markdown`.
- Commit the story's records (its `.sdlc` files: claim, steps, receipts, traces, and the shared records its work added) on the story branch together with the code before `pull_request.create` and before each `pull_request.update`, so merging the pull request brings them to the base branch. They travel outside the code's write scope (`orchestration_policy.story_records.in_branch`); records of other stories and `.sdlc/config.json` never do. A checkpoint without them warns, or is refused when `story_records.before_pull_request` is `refuse`.
- Before the test record and before the pull request, run `story sync --id <story>` to align the story branch with the base branch without losing local records (see "Standard pull-request delivery sequence" in the skill). After a passed merge completion and after the lifecycle-complete gate, the plugin publishes the story's `.sdlc` records to the base branch by itself; report to the user any failure it prints.
- After the lifecycle-complete gate, when it warns that the closing records are not on the remote base branch, run `story publish-records --id <story>`: it pushes a branch with only those records (and opens its pull request when `story_records.publish_pull_request` names a provider) without changing the checkout. Tell the user the branch or pull request to merge.
- Protected-branch merge, deployment, and production access stay outside this command. After the verified `pull_request.create` completion (and any later `pull_request.update`), close the delivery with `autonomy delivery close --terminal-status ready_for_review` before the lifecycle-complete gate.
- If the user merged the pull request on GitHub themselves, give them the command to acknowledge it in their own terminal and never run it for them: `autonomy delivery reconcile --id <profile-id> --pr-url <url> --actor-type human --approval-source explicit-user --summary "<their words>"`. It is refused inside an agent session. The delivery then ends `merged_externally` (or keeps `ready_for_review` and gains the receipt), and the final certification is labelled `externally_reconciled`. `status` points to the command when it sees such a merge.
- When an active standing approval the user already gave covers this exact kind of pull request (`autonomy standing status`), pass `--standing-approval <id>` instead of asking for the work brief, working-mode, and action confirmations, and leave out `--code-review`: the delivery takes the standing approval's code review answer and you do not ask again. If the user answers differently for this story, the delivery is outside the standing approval and takes the normal question and approvals. It never covers merge. If any step answers `checkpoint_required` with `standing_approval.reasons`, stop and ask the user for the normal confirmation. Never create or widen a standing approval without the user's explicit approval.
- If `$ARGUMENTS` is empty, ask for the requirement before touching any record.
- Before `task start`, run `story availability --id <story> --json`. When `safe_to_start` is false, stop and show the user the plain-language line it prints (who reserved or holds the story and until when, or the branch or pull request that names it), and ask whether to continue. Never pass `--force` on their behalf.
- Run `task start` and `story claim` at the start of development, not at integration.
